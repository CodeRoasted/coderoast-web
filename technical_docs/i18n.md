# CodeRoastWeb Internationalisation

CodeRoastWeb currently supports English and French. The translation system is intentionally static and type-checked: all UI copy is imported at build time, and TypeScript rejects locale drift.

## File Layout

| File | Role |
|---|---|
| `src/i18n/en.ts` | English source of truth. |
| `src/i18n/fr.ts` | French bundle typed as `typeof en`. |
| `src/i18n/translations.ts` | Aggregates `{ en, fr }` and exports `TranslationKey`. |
| `src/hooks/useTranslation.ts` | Returns the active locale tree. |
| `src/store/useStore.ts` | Stores `language: 'en' | 'fr'`. |
| `src/components/LanguageToggle.tsx` | User-facing language switch. |

## Type Safety Model

`translations.ts` derives the public translation type from English:

```ts
const translations = { en, fr } as const
export type TranslationKey = typeof translations.en
```

`fr.ts` imports the English type:

```ts
import type en from './en'
const fr: typeof en = { ... }
```

This means:

- missing French keys fail TypeScript;
- extra or wrongly-shaped French keys fail TypeScript;
- consumers get autocomplete from `useTranslation()`;
- adding a key is a compile-time workflow, not a runtime surprise.

## Runtime Flow

```text
LanguageToggle -> useStore.setLanguage('en' | 'fr')
			   -> useTranslation()
			   -> translations[language]
			   -> component render
```

No route reload is needed. The active language is memory-only today; it is not persisted to local storage or cookies.

## Using Copy

```tsx
import { useTranslation } from '@/hooks/useTranslation'

export default function MyComponent() {
	const t = useTranslation()
	return <h1>{t.hero.tagline}</h1>
}
```

Do not hard-code user-visible copy in components unless it is temporary developer-only text. If a string is visible in the shipped UI, put it in both locale files.

## Adding A Translation Key

1. Add the key to `src/i18n/en.ts`.
2. Add the matching key to `src/i18n/fr.ts`.
3. Use it through `useTranslation()`.
4. Run `npm run build` or `npm test` to catch shape drift.

Prefer grouping keys by route or feature (`lab`, `logcraft`, `cookiePrefs`, `useCases`) rather than by component type.

## Adding A Language

1. Create `src/i18n/<locale>.ts` with `const locale: typeof en = { ... }`.
2. Add the locale to `translations` in `src/i18n/translations.ts`.
3. Extend `type Language` in `src/store/useStore.ts`.
4. Update `LanguageToggle.tsx` to expose the new locale.
5. Add tests or update translation parity tests if they assume only EN/FR.

## Copy Guidelines

- Keep LogCraft product terms stable across languages: `LogCraft`, `Lab`, `InSight`, `MetaLog`, `ECS`, `OTLP`, `WebSocket`.
- Translate UI intent, not literal syntax. YAML examples and API paths should stay as code.
- Avoid changing object structure just to tweak copy; change leaf strings where possible.
- Keep arrays aligned between locales when UI maps by index.

## Tests

The translation tests live under `src/test/translations.test.ts`. They should cover at least:

- EN/FR structural parity;
- important route copy existing in both locales;
- no accidental missing nested keys after refactors.

Run:

```sh
npm test -- translations
```
